# Server Authentication — Phase 1

Implement server-side authentication as a required security boundary before adding remote desktop sessions, noVNC, or any other privileged UI surface.

This phase is **server-only**. It establishes first-run pairing, persistent device credentials, authenticated HTTP/WebTransport access, device revocation, and a secure one-time pairing grant that later desktop and mobile clients can consume.

This is a deliberate breaking change. There is **no backwards compatibility** with unauthenticated clients, legacy unauthenticated routes, freely mintable API tokens, or clients that do not participate in pairing. Existing desktop and mobile clients must be updated in a later client phase before they can connect to a server implementing this plan.

---

## 0. Goals

- Require authentication for every sensitive server endpoint by default.
- Make the initial server connection possible without opening an infrastructure/provider dashboard.
- Generate a one-time pairing URL when the server is first started.
- Allow a desktop client to exchange that pairing material for its own persistent device credential.
- Allow an authenticated desktop client to create short-lived, one-time grants for mobile QR pairing.
- Store device and grant metadata in the existing SQLite database.
- Never store reusable raw device tokens in the database.
- Support explicit device revocation and revoke-all operations.
- Authenticate WebTransport during its handshake and bind the authenticated device to the connection.
- Keep authentication local and cheap: normal requests validate a signed credential without a database round trip.
- Fail closed when the server cannot initialize its authentication state.

## 1. Non-goals

- No provider authentication or provider API-key management. Those credentials are a separate concern.
- No VNC/noVNC implementation in this phase. Phase 1 only protects the future desktop-session surface.
- No user accounts, email login, multi-tenant organization model, or cloud identity provider.
- No anonymous mode or compatibility flag.
- No query-string bearer tokens for ordinary HTTP API calls.
- No permanent secret embedded in a QR code.
- No attempt to preserve the current freely mintable `/api/auth/token` behavior.

## 2. Current implementation to replace

The repository already contains an HMAC token issuer in `apps/server-go/internal/auth/token.go` and middleware in `internal/routes/api_token.go`.

That implementation is useful groundwork but is not an acceptable final boundary for Phase 1:

- `POST /api/auth/token` accepts a device ID and mints a token without proof of pairing.
- The default token lifetime is five minutes, which is appropriate for a handshake credential but not a persistent device session.
- Revocations are memory-only.
- `RequireAPIToken` is mounted only on selected routes; the main Fiber surface is currently mostly unauthenticated.
- Query-string tokens are accepted, which is unsuitable for normal API access because URLs leak through logs, history, referrers, and diagnostics.
- A failed token-secret persistence operation falls back to an ephemeral secret. Phase 1 must fail startup instead, because otherwise a restart silently invalidates all devices.

Phase 1 should replace this behavior rather than layer a compatibility path around it.

## 3. Security model

### 3.1 Server identity

On first start, the server creates a persistent authentication state in the Console storage directory. The state includes:

- A random server signing secret, at least 32 bytes.
- A random server identifier.
- A human-readable server name, defaulting to the machine/server hostname or an explicit configuration value.
- A first-run pairing grant.

The secret file and containing directory must be created with restrictive permissions (`0700` directory, `0600` file). If the server cannot read or create this state, startup fails with an actionable error. Do not silently generate an ephemeral replacement.

The signing secret is not stored in SQLite and is never returned to clients.

### 3.2 Credential types

Use separate credential types with separate validation rules:

1. **Bootstrap pairing grant**
   - Created at first run or explicitly regenerated by an operator.
   - Short-lived and one-time.
   - Used only to pair the first desktop/device.
   - Never accepted as a general API bearer credential.

2. **Device session token**
   - Issued only after a valid pairing exchange.
   - Long-lived enough for normal regular use.
   - Signed by the server secret.
   - Contains a device ID, token ID, issued time, expiry, and token version.
   - Stored only in the client’s secure credential store.
   - The server stores only a hash/identifier sufficient for revocation and audit.

3. **Mobile QR pairing grant**
   - Created by an already authenticated device.
   - Short-lived, single-use, and scoped to pairing one new device.
   - Contains server metadata needed for the mobile client to connect.
   - Must not contain the creating device’s reusable session token.

4. **WebTransport connection authorization**
   - A device session token may be presented during the handshake.
   - Validate once during handshake and bind the resulting device identity to the connection.
   - Do not require a new authentication exchange for every frame.

### 3.3 Token format

Use a versioned, signed, URL-safe format. HMAC-SHA256 with a random server secret is acceptable for this single-server deployment.

Payload fields should include:

```json
{
  "v": 1,
  "kind": "device",
  "device": "device-id",
  "jti": "token-id",
  "iat": 1760000000000,
  "exp": 1762592000000
}
```

Use constant-time signature comparison. Reject unknown versions, unknown kinds, missing IDs, malformed timestamps, tokens exceeding a reasonable size, expired tokens, and revoked devices/tokens.

Do not put API credentials or provider credentials in these payloads.

## 4. Pairing flow

### 4.1 First-run bootstrap

At startup:

1. Load or create the persistent server auth state.
2. Ensure the database auth tables exist.
3. Create a bootstrap pairing grant if no device has ever been paired, or if an operator explicitly requests a new bootstrap grant.
4. Print a pairing URL to the server log/terminal.
5. Do not print the server signing secret or any long-lived device token.

The URL should use a fragment for the secret so it is not sent in HTTP requests or normal access logs:

```text
https://server.example/console/pair#v=1&server=<server-id>&grant=<one-time-grant>
```

The URL is a transport for pairing data, not an authenticated API URL. The client must exchange the grant immediately and then discard it.

If the server is configured for plain HTTP in a trusted local network, print a warning. Authentication protects access, but production remote use should still use TLS. The existing WebTransport configuration already has TLS-related startup behavior and should remain the source of transport configuration.

### 4.2 Desktop exchange

Add a public, narrowly scoped endpoint:

```text
POST /api/auth/pair
```

Request:

```json
{
  "grant": "...",
  "deviceName": "My desktop",
  "platform": "desktop"
}
```

Response:

```json
{
  "success": true,
  "data": {
    "server": {
      "id": "...",
      "name": "...",
      "version": "..."
    },
    "device": {
      "id": "...",
      "name": "My desktop"
    },
    "token": "...",
    "expiresAt": 1762592000000
  }
}
```

The endpoint must:

- Validate the grant signature, kind, expiry, and server ID.
- Atomically mark the grant as consumed.
- Reject reuse, expiry, malformed input, and excessive request size.
- Create a device record.
- Issue a device session token.
- Return the token exactly once.
- Never return the raw bootstrap grant after exchange.

If this is the first successful pairing, mark bootstrap setup complete. There must be no endpoint that can mint a device token from only a caller-supplied device ID.

### 4.3 QR pairing from an authenticated desktop

Add an authenticated endpoint:

```text
POST /api/auth/pairing-grants
```

Request:

```json
{
  "deviceName": "My phone",
  "platform": "android"
}
```

Response:

```json
{
  "success": true,
  "data": {
    "server": {
      "id": "...",
      "name": "...",
      "baseUrl": "https://server.example"
    },
    "grant": "...",
    "expiresAt": 1760000030000
  }
}
```

The grant must:

- Be valid for a short window, such as 60 seconds.
- Be single-use.
- Be scoped to the authenticated creating device and the requested target platform/name.
- Be stored as a hash, never as raw grant material.
- Be invalidated after successful exchange or explicit revocation.
- Not contain the creator’s bearer token.

The desktop renders the returned payload as a QR code. The mobile app scans it, displays the server name and address for confirmation, then calls `POST /api/auth/pair` and stores the returned device token in Android encrypted storage.

## 5. Database design

Add an additive schema section to the existing server database initialization, but do not preserve old unauthenticated auth behavior. The tables should be idempotent for startup and use SQLite constraints.

### 5.1 `auth_devices`

Suggested fields:

```sql
CREATE TABLE IF NOT EXISTS auth_devices (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    platform TEXT NOT NULL,
    token_id TEXT NOT NULL UNIQUE,
    token_hash BLOB NOT NULL,
    created_at INTEGER NOT NULL,
    last_seen_at INTEGER,
    revoked_at INTEGER,
    metadata_json TEXT NOT NULL DEFAULT '{}'
);
CREATE INDEX IF NOT EXISTS idx_auth_devices_active
    ON auth_devices(revoked_at, last_seen_at);
```

Store only a cryptographic hash of the raw device token, or a hash of its token ID plus a server-side secret. Never store a bearer token in plaintext.

### 5.2 `auth_pairing_grants`

```sql
CREATE TABLE IF NOT EXISTS auth_pairing_grants (
    id TEXT PRIMARY KEY,
    grant_hash BLOB NOT NULL UNIQUE,
    kind TEXT NOT NULL,
    creator_device_id TEXT,
    target_platform TEXT NOT NULL,
    target_name TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    expires_at INTEGER NOT NULL,
    consumed_at INTEGER,
    revoked_at INTEGER
);
CREATE INDEX IF NOT EXISTS idx_auth_pairing_grants_expiry
    ON auth_pairing_grants(expires_at, consumed_at, revoked_at);
```

Use a transaction for consume-and-issue so two concurrent requests cannot use the same grant.

### 5.3 Cleanup

Purge expired and consumed grants periodically and at startup. Keep revoked device rows for audit and explicit device-list display; do not silently delete them during ordinary cleanup.

## 6. HTTP route policy

Implement one top-level authentication middleware with an explicit public allowlist. The default must be protected; new routes must not accidentally become public.

Public routes should be limited to:

- `GET /health` (if needed for process supervision; it must not reveal sensitive state).
- `GET /api/version` (optional, only non-sensitive build metadata).
- `POST /api/auth/pair` (bootstrap and QR grant exchange).
- A narrowly scoped endpoint for reading the non-secret bootstrap pairing metadata, only if the chosen bootstrap UX requires it.

Everything else must require a valid device session token, including:

- Filesystem and worktree routes.
- Git routes.
- Terminal and PTY routes.
- Project scripts and background jobs.
- Port forwarding and port registry routes.
- Sessions, runs, chat streams, notifications, and device routes.
- Provider credentials and OAuth callbacks after their pairing/session requirements are defined.
- Debug routes.
- Future remote desktop/noVNC routes.

`OPTIONS` requests may pass through only as required by the configured CORS policy. Do not use a broad unauthenticated CORS exception.

On failure, return one generic `401 Unauthorized` response. Do not reveal whether a token was unknown, expired, revoked, or malformed.

### Authorization header

Require:

```http
Authorization: Bearer <device-session-token>
```

Remove ordinary API support for `?token=`. Query parameters may be accepted only in a separate, explicitly scoped WebTransport handshake path if the underlying client cannot set headers, and that path must still validate the same device credential and avoid logging the URL.

The middleware should place the authenticated device ID in Fiber locals for downstream audit and authorization checks.

## 7. WebTransport integration

Use the same server auth issuer and device records for Fiber and WebTransport.

At handshake:

1. Extract the bearer credential from the supported handshake location.
2. Validate signature, version, kind, expiry, and device revocation.
3. Attach the device ID to the WT connection/session context.
4. Update `last_seen_at` asynchronously or with a throttled write.
5. Reject unauthorized handshakes before creating a session or allocating privileged resources.

After acceptance, do not validate the token per frame. The authenticated connection context is the authorization boundary for that WT session.

A revoked device must not create new connections. Existing connections should be closed when practical after revocation; at minimum, revocation must prevent reconnect and must be checked at explicit high-value connection operations.

## 8. Device management endpoints

All endpoints below require authentication:

```text
GET    /api/auth/devices
DELETE /api/auth/devices/:id
POST   /api/auth/devices/revoke-others
POST   /api/auth/pairing-grants
```

Rules:

- A device may rename itself.
- A device may revoke another device.
- Revoking the current device should revoke its token and return a response that tells the client to clear local credentials.
- Revoke-all-others must never revoke the current device.
- A revoked device cannot be unrevoked; it must pair again.
- Device IDs and names must be validated and length-limited.

## 9. Startup and configuration behavior

Add server configuration for:

- Server display name.
- Auth storage path, reusing the existing Console storage directory conventions.
- Pairing grant lifetime.
- Device token lifetime.
- Optional requirement for TLS before allowing non-loopback pairing.

Startup must fail if:

- The signing secret cannot be loaded or created.
- The database cannot create auth tables.
- The configured auth storage permissions cannot be enforced.
- The server is configured to expose a non-loopback address without the required transport security policy.

Log only safe identifiers and events:

- Pairing grant created (never the grant itself).
- Device paired (device ID, platform, name).
- Device revoked.
- Authentication failure counts, without token material.

Never log Authorization headers, raw grants, QR payloads, provider keys, or full pairing URLs containing secrets.

## 10. Package layout

Suggested server package split:

```text
internal/auth/
  state.go          server secret and server identity
  credentials.go    token and grant formats, signing, validation
  pairing.go        grant creation and exchange
  devices.go        device records and revocation
  middleware.go     Fiber and shared request authentication
  errors.go

internal/db/
  schema.go         auth tables and indexes
  auth_store.go     transactional device/grant queries

internal/routes/
  auth_pairing.go   pair, grant, device-management endpoints
  routes.go         protected-by-default route registration

internal/wt/
  auth.go           handshake credential extraction and binding
```

Keep provider authentication separate from this package. Do not reuse provider OAuth state for server/device authentication.

## 11. Tests required for Phase 1

Add focused server tests under `apps/server-go/tests/` and package tests where appropriate.

### Credential tests

- Valid device token verifies.
- Invalid signature fails.
- Unknown version/kind fails.
- Expired token fails.
- Revoked device fails.
- Token size and malformed input are rejected.
- Constant-time signature path is used.
- Secret persists across issuer/server restart.
- Startup fails when the secret cannot be persisted.

### Pairing tests

- First-run bootstrap grant can pair exactly one device.
- Bootstrap grant cannot be reused.
- Expired grant fails.
- QR grant requires an authenticated creator.
- QR grant is single-use under concurrent exchange.
- QR grant is scoped to its server and target metadata.
- Raw grants are not present in database rows or logs.
- Pairing returns a token once and the client can use it on the next request.

### Middleware and route tests

- Every sensitive route returns 401 without a credential.
- Every sensitive route returns 401 for malformed, expired, and revoked credentials.
- Public routes remain limited to the explicit allowlist.
- Authorization header parsing is strict.
- Query-string tokens are rejected on ordinary HTTP routes.
- Authenticated device ID is available to handlers.
- Error responses do not distinguish token failure reasons.

### Database tests

- Auth tables initialize on a fresh database.
- Existing application data remains readable after schema initialization.
- Device revoke is transactional.
- Grant consume-and-issue is atomic.
- Expired grants are cleaned up safely.

### WebTransport tests

- Authenticated handshake succeeds and binds the device ID.
- Missing/invalid/revoked credentials fail before session allocation.
- A valid connection does not revalidate every frame.
- Revocation prevents a new handshake.

Run only the relevant server test packages while implementing; do not run the repository-wide suite.

## 12. Breaking-change checklist

- [ ] Remove the current freely callable `POST /api/auth/token` contract.
- [ ] Do not retain an unauthenticated fallback mode.
- [ ] Do not accept caller-selected device IDs as proof of identity.
- [ ] Remove ordinary `?token=` API authentication.
- [ ] Mount protected-by-default middleware before registering sensitive routes.
- [ ] Update route tests that currently assume unauthenticated access.
- [ ] Update server startup to fail closed on auth-state persistence errors.
- [ ] Document that old clients must upgrade and pair again.
- [ ] Do not add desktop/mobile compatibility code in this phase.

## 13. Completion criteria

Phase 1 is complete when:

1. A fresh server starts, creates persistent auth state, and prints a one-time pairing URL without leaking its secret.
2. An unpaired client can use only the pairing exchange endpoint and harmless health/version endpoints.
3. A paired device receives a persistent token and can authenticate every normal HTTP request automatically.
4. A second device can be paired only through an authenticated, short-lived, one-time QR grant.
5. Revoking a device prevents its future HTTP and WebTransport access.
6. No sensitive route remains accidentally public.
7. The server has no fallback that accepts the old unauthenticated or freely mintable token behavior.
8. All focused Phase 1 server tests pass.
9. The future VNC/noVNC route can be added behind the same middleware without introducing another authentication mechanism.

## 14. Follow-up phases

- **Phase 2 — desktop client:** secure OS credential storage, paste pairing URL, device list, QR generation, reconnect behavior.
- **Phase 3 — mobile client:** QR scanner, server confirmation screen, encrypted token storage, reconnect and revocation handling.
- **Phase 4 — remote desktop:** lightweight Linux desktop lifecycle, VNC/noVNC WebSocket proxy, resize/clipboard/input controls, and strict per-device authorization.
